## 2. Entry View — Skip Questions Without an Answer (rollbar-undefined-answer)

### 2.1 Group-entry view skips a newly-added group question without crashing

> The Rollbar fix in `fetch-answers.js` / `fetch-branch-answers.js` applies to **group inputs only**:
> the `typeof answers[ref] !== 'undefined'` guard was added inside the `case GROUP:` block. The crash occurred
> when a question was added *into a group* after the entry was collected, leaving the stored entry without

- **Manual Action:**

  2. Sync/download that form's project on the app (so an older entry now has a group input without an answer).
  3. Open the old entry in Entry View.
  4. Verify the entry renders, the new group question is skipped, and there is no crash.

## 6. Download Flow — Project Version Check

> Before downloading entries, the app now checks if the local project structure is in sync with the
> server. If the project has been updated on the server (e.g. a new question added to a group),
> the app prompts the user to update the project first, then proceeds with the download. This
> prevents the downloaded entries from being rendered with a stale project model, which caused
> group questions added after entry collection to be skipped silently.
>
> Additional safeguards:
> - Download buttons are disabled while a version check or download is in progress (`isFetching` / `promptOpen`).
> - After a project update, the download cache is cleared so stale page URLs and entry counts are not reused.
> - Existing remote entries for the form are deleted before downloading to avoid duplicates.
> - The download warning message now clarifies that entries will be **replaced** (not just removed).

### 6.1 Download prompts for project update when structure is out of sync

- **Test Description:** On a device with an outdated project structure (e.g. a question was added to a group on the server after the entry was downloaded), tap to download entries. Verify the app detects the version mismatch and prompts the user to update the project first.
- **Expected Result:** A confirmation dialog appears: "Update form on your device?" with the message "Form has been updated." If the user confirms, a "Wait…" progress dialog appears while the project updates. After the update completes, the download proceeds. All group questions (including newly-added ones) appear in the downloaded entries.
- **Manual Action:**
  1. On the web admin, add a new question to an existing group in a project.
  2. On the app, open the project (do not re-select it from the project list, so the local structure remains outdated).

  4. Verify the "Update form on your device?" dialog appears.
  5. Confirm the update.
  6. Verify the "Wait…" progress dialog appears while the project updates.
  7. Verify the download proceeds and the newly-added group question appears in the downloaded entries.

## 7. Stacked Modal Dismissal

> Fix for: `Cannot read properties of null (reading 'nextSibling')`.
> `modalsHandlerService.dismissAll()` used to dismiss every open modal simultaneously,
> causing a DOM unmount race in the Ionic/Vue overlay (teleport) teardown. It now dismisses
> stacked modals one at a time, from the topmost (last presented) to the bottom one, awaiting
> each dismissal. Every login flow (standard, passwordless, Google, Apple, email verification)
> closes its modals through `dismissAll()`.

- **Test Description:** Complete a passwordless (magic link) login while the login, send-email, and code-entry modals are stacked on top of each other. Verify all modals close and the app does not crash.

- **Manual Action:**
  1. Build and install the app (Android or iOS) pointing at the staging server.
  2. Log out if a session is already active.
  3. Open a page that requires login (e.g. Add Project, or open a private project).
  4. On the login modal, switch to passwordless login.
  5. Enter the email and submit — the send-email modal opens on top of the login modal.
  6. Enter the 6-digit code — the code-entry modal opens on top of the send-email modal (3 modals stacked).
  7. Tap **Login** and watch the modal stack close.
  8. Verify: no crash, all modals gone, toast shown, no `nextSibling` error in the console.

## 8. Deferred Project Update After Login (No Active Project)

> Fix for: `Cannot read properties of undefined (reading 'details')` in `projectModel.getSlug()`.
> When a project update fails with an auth error (e.g. expired JWT), the retry is stored in
> `rootStore.afterUserIsLoggedIn.callback` and fired again after the next login. If the user has
> left the project context (e.g. is on the Add Project page), the project model is empty and the
> retry used to crash. Now the update is skipped cleanly whenever no project is loaded
> (a console warning `updateProject skipped: no active project` may be logged, which is expected).

### 7.1 No crash after passwordless login with a pending update and no active project

- **Test Description:** Reproduce the exact crash scenario: expired JWT mid-update → login retry stored → user on a page with no active project → passwordless login → retry must be skipped without crashing.
- **Expected Result:** After login completes there is **no crash**, no white screen, and no Rollbar error `Cannot read properties of undefined (reading 'details')`. The user stays on the current page and the login success toast appears. A console warning `updateProject skipped: no active project` may be logged (expected).
- **Manual Action:**
  1. Configure the staging server with a short JWT TTL (~5 minutes).
  2. Build and install the app pointing at the staging server.
  3. Log in and open a project whose structure is outdated (so the version check triggers an update).
  4. Wait for the JWT to expire.
  5. Force the project update (re-open the project / navigate into its entries) so the update request fails with an auth error — a toast appears and the login modal opens.
  6. Dismiss the login modal (swipe down) and navigate to a page with no active project (e.g. **Add Project**).
  7. Open the login modal again and complete a passwordless login (send email + enter code).
  8. Verify: no crash, user stays on the page, toast shown, no `details` error in the console or Rollbar.

### 7.2 Deferred update still runs when a project is loaded (regression)

- **Test Description:** Same expired-JWT setup, but the login is completed while the user is still on the project page (a project IS loaded), so the deferred update must run normally.
- **Expected Result:** The deferred project update runs: the "Updating project…" progress dialog is shown, the update-result alert appears, and entries reload. No crash.
- **Manual Action:**
  1. Using the same short-JWT staging setup, open a project with an outdated structure so an update is triggered.
  2. Let the JWT expire mid-update so an auth error occurs and the login modal appears.
  3. Complete the login immediately while still on the project page (do not navigate away).
  4. Verify the deferred update completes normally (progress dialog, result alert, entries loaded).

> Note: the `updateProject()` entry in `src/use/project/update-project.js` (used by the Entries Upload page) carries the same empty-project guard defensively. It is not reachable from the UI without an active project, so it has no separate staging check; the shared `versioningService.updateProject()` guard exercised in 2.1 and 2.2 covers the same empty-model path.
